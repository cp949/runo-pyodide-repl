# TRP-005 자동화 입력은 새 프롬프트가 보인 뒤에 보내야 한다(활성 읽기 전 키는 버려진다)

- 상태: ACTIVE
- 적용 조건: 브라우저 하니스(Playwright)가 Enter 뒤 이어서 키를 보낼 때. 읽기를 요청하는 코드(REPL 읽기, `input()`)를 추가하거나 읽기 시작 경로를 바꿀 때.

## 오해하기 쉬운 신호

- 오류가 나지 않는다. 화면에 입력이 없을 뿐이다.
- 대기가 길면 통과한다. Enter 뒤 `z`를 치기까지의 지연별 들어온 비율(Chromium 148 headless, N=10, worker 없는 읽기 루프): 0ms 0/10, 5ms 2/10, 10ms 2/10, 20ms 이상 10/10. 그래서 운이 좋으면 통과하고 짧으면 실패하는 불안정한 시험이 된다.
- 눈으로 보는 수동 확인에서는 재현되지 않는다(사람은 그 창 안에서 치지 않는다).

## 원인

`Readline.read()`는 입력 상태와 `activeRead`를 `term.write("", cb)` 콜백 안에서 만든다. Enter로 읽기가 끝난 뒤 다음 읽기의 콜백이 오기 전에는 활성 읽기가 없고, 벤더 `readKey`는 이때 Ctrl+C·Ctrl+L 외 단일 키를 버린다(붙여넣기는 낡은 `State`에 그린다). 다음 읽기를 worker 요청으로 시작하는 구성(RD-005부터)에서는 왕복 시간과 실행 시간이 더해져 창이 길어진다.

## 탐지/회피

- 회피: 입력 전에 새 프롬프트 행이 화면에 나타난 것을 기다린다. 프롬프트를 그리는 콜백이 `activeRead`를 같은 콜백에서 설정하므로 프롬프트가 보이면 읽기는 이미 활성이다. 고정 `sleep`으로 대신하지 않는다.
- 탐지: 하니스의 입력 직전에 프롬프트 행 대기가 있는지 본다. 지연을 0으로 낮춰 돌려 시험이 실패하는지 확인한다.
- 근본 해소는 활성 읽기가 없는 동안의 입력을 버퍼링하는 것이다(3.14 pty는 tty가 버퍼링한다). `10-parity-deviations.md` 32.
