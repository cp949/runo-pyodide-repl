# 출력으로 커지는 접두가 뷰포트를 넘으면 윗행이 안 보이고, 개행 없는 조각이 이어지면 쓰기량이 초선형이다

Status: deferred
Origin: RD-022b 독립 second-opinion 리뷰(가설 SO-V3a0·SO-V3b), 벤더 jsdom 재현·관찰. 브라우저·사용자 시나리오 미관찰.

## 현상

1. 뷰포트 초과(SO-V3a0): 열린 읽기 중 개행 없는 배경 출력이 쌓여 `접두 + 프롬프트 + 입력`이 화면 행 수를 넘으면 벤더 `refresh()`의 뷰포트 창(5.6.7과 같은 계산)이 접두 윗행을 그리지 않는다. 읽는 동안에는 그 행이 화면·스크롤백 어디에도 없다. 다음 완성 행이 오면 접두 전체를 `lines`로 다시 쓰므로 최종 유실은 없다(리뷰가 같은 조건의 중복·유실 가설 SO-V3a를 기각).
   - 재현(`StubTerminal` cols 10·rows 4): `read("> ")` → `ab` → `printAboveRaw("", "p".repeat(45))`.
   - 실제: 화면+스크롤백의 `p` 35개, 편집 한 번(`c`) 뒤 25개. 기대: 45개.
2. 쓰기량(SO-V3b): 개행 없는 조각이 연속으로 오면(점 찍기 진행률) 조각마다 접두 전체를 지우고 다시 쓴다.
   - 관찰(cols 200·rows 50, `>>> `, 조각 `.` N개): N=100 → 8879 B, N=400 → 97677 B, 비율 11.0(선형이면 약 4, 제곱이면 약 16). 성능 수치는 판정이 아니다(`docs/design/09-testing.md` 9.7).

RD-022b checklist "제외"의 "뷰포트 초과 입력(5.6.7)"은 입력 기준이라 출력으로 커지는 접두는 포함하지 않았다(리뷰 반영 때 제외 항목에 추가).

## 완료 기준

접두가 폭의 배수로 찬 행을 완성 행(`lines`)으로 내보내 접두를 한 행 이하로 유지하는 등으로, 위 재현에서 `p` 45개가 읽는 동안 화면+스크롤백에 있고 N에 대한 쓰기량 비율이 선형(약 4)에 가깝다는 jsdom 시험. 또는 문서화만 유지한다.

## 재개 조건

긴 개행 없는 배경 출력(진행 점 찍기 등)으로 화면이 느려지거나 출력 일부가 읽는 동안 사라진 것이 관찰될 때.
